Conceptual Framing

How the engine maps to React conventions, and why

The QMS Workflow Engine is a Python framework for defining interactive workflow forms that render as HTML for humans and serialize as JSON for AI agents — same state, same actions, same URLs, one source of truth. This page documents how it aligns with the component vocabulary most web developers already know.

The engine grew from first principles — HATEOAS affordances, faithful projection, stateless server — and landed at a shape recognizably adjacent to React. The alignment is intentional in the vocabulary and accidental in the architecture.

If you already know the codebase, skip to §1. If you’re new to the engine, the primer below walks through the vocabulary, the core loop, and a minimal example first. The rest of the page assumes the primer.

★ Primer

00 Before the comparison — what is this engine?

The rest of the page assumes you know what a component is, what bind() does, and why anyone would care. This section establishes that vocabulary from scratch. Skip it if you already know.

The problem the engine solves

Most applications present different surfaces to humans and programs. A human sees a web form; a program sees a REST API; a mobile client sees something in between. The three surfaces drift apart over time because they are maintained separately. When an AI agent enters the picture — reading a page, deciding an action, submitting a change — the drift becomes painful. Agents need structured data that humans don’t want to see; humans need layout that programs don’t care about; both need to agree about what actions are available right now.

The QMS Workflow Engine collapses these surfaces. A single Python definition produces an interactive page that a browser renders as HTML and an AI agent consumes as JSON. The two views describe the same state. The two clients take the same actions against the same URLs. When the definition changes, both views update. This property is called faithful projection and is enforced at CI time by a parity test that compares every URL exposed in JSON to every clickable element rendered in HTML.

The central idea: a component

A component is a self-contained form element. A text input is a component. A container of tabs is a component. A whole page is a component. The vocabulary is uniform all the way up and down. Components compose — a container component holds child components, and the tree itself is a component.

Each component preserves its identity under transformation — it serializes, renders, handles actions, and recomposes without losing the thing it is.

Every component does four things:

  • Serialize itself to JSON — current state, plus a list of available affordances (see below).
  • Render itself to HTML — styled for a browser, with the same affordances exposed as buttons and forms.
  • Handle incoming actions — a POST from either client mutates the stored state.
  • Announce what the client can do right now — via affordances, a list of URL + POST-body pairs with human-readable hints.

This last property is the HATEOAS style (Hypermedia As The Engine Of Application State): the server tells the client what the client can do. An agent doesn’t need an external schema. It reads the page, finds the affordances, and picks one. Human buttons and agent POSTs are driven by the same affordance list.

The core loop

Four stages. Every request walks the cycle.

1Define

A Python file in pages/ exports a seed — the structural definition of the page. No state; no identity. Re-read every request.

2Bind

The server attaches a per-instance JSON file (the Store) to the seed, producing a live tree of bound components with scoped keys.

3Serve

The bound tree renders to HTML (for browsers) or serializes to JSON (for agents). Both include affordances for the next action.

4Handle

The client POSTs an action. The server binds again, walks to the target, calls its _handle(), updates the Store, and responds with the new state.

↶ After Handle, the next request starts again from Define — the server holds no long-lived in-memory state. Every request is a fresh bind.

Key vocabulary

The terms below appear throughout the rest of this page. Bookmark this section if needed.

Seed
The Python-code definition of a page’s structure. Lives in pages/*.py, exported as definition = PageComponent(...). Immutable at runtime. Holds callables (lambdas, validators) that cannot round-trip through JSON.
Store
A per-instance JSON file. One file per bound page instance, at data/{instance_id}.json. Holds all mutable state — current values, active tab, descriptor overrides.
Bind
The operation that attaches a Store to a seed and recursively produces a live tree of components. Scopes each child by key. Happens on every request.
Descriptor
A JSON-serializable snapshot of a component tree — its props (configuration values) and its children’s descriptors. Stored as __structure in the Store. The canonical source of truth for any runtime-editable structure.
Key
A string identifier unique within a container scope. Used for routing, Store scoping, and matching descriptors to seeds. Think of it as the component’s identity.
Scope
The parent container’s namespace. A child’s Store entries are prefixed with the scope to keep siblings separated.
Affordance
A declared action: URL, HTTP method, POST body template (with placeholders like <value>), and a human-readable hint. Emitted identically in JSON and HTML so the two clients always see the same action list.
Faithful projection
The principle that HTML is a derivation of JSON — the two express the same state and the same actions. Enforced at CI time by tests/test_parity.py, which compares affordance URLs in JSON against data-c-* attributes in HTML for every page.
HATEOAS
Hypermedia As The Engine Of Application State. A client discovers what it can do by reading what the server sent, not by reading external documentation. The engine exposes all actions as affordances; the client never needs a separate schema.
Handle
The method _handle(body) that each component implements to process an action. Interprets the action name, mutates the Store, returns the updated state.
Container vs leaf
A container component holds children (PageComponent, NavigationComponent, GroupComponent, etc.). A leaf holds a primitive value (TextComponent, NumberComponent, BooleanComponent, etc.).

A minimal example

The smallest useful page: a label plus a single text input.

# pages/hello.py
from engine.pagecomponent import PageComponent
from engine.textcomponent import TextComponent

definition = PageComponent(
    key="hello",
    label="Hello Page",
    components=[
        TextComponent(key="name", label="Your name"),
    ],
)

What happens on first request

  1. Server discovers pages/hello.py and imports the seed.
  2. Server calls seed.bind(data_dir, scope="hello"). Store is created if missing; empty.
  3. PageComponent recursively binds its children. TextComponent is now a live instance scoped to hello/name.
  4. JSON request: serialize() returns {key: "name", value: null, affordances: [{method: "POST", url: "/pages/hello/name", body: {action: "set_value", value: "<str>"}}]}, wrapped by PageComponent’s own serialization.
  5. HTML request: render() produces a styled input with the same URL as a data-c-post attribute. The parity test verifies the URL matches.

What happens when the user types “Alice” and submits

  1. Browser POSTs {"action": "set_value", "value": "Alice"} to /pages/hello/name.
  2. Server binds the seed again (fresh tree; no memoization across requests).
  3. Server walks path name to locate the TextComponent child, calls _handle({"action": "set_value", "value": "Alice"}).
  4. TextComponent writes "Alice" to Store key hello/name.
  5. Server re-serializes the full page. Returns JSON or morphs-in HTML, depending on the client.
  6. Next GET reads the same Store. TextComponent binds with value="Alice". is_complete returns True. Page reflects the update.

That is the entire engine. Everything else — tabs, tables, conditional visibility, cross-field validation, page builders — is a variation on this loop with richer component types and richer affordances.

You now have enough vocabulary to read the rest of the page. Every React-side term maps to something in the list above. When you see bind, picture a seed meeting a Store. When you see “affordance,” picture a URL-plus-POST-body pair that both humans and agents can use. When you see __structure, picture the JSON snapshot of a container’s children.

01 Thesis

The architecture grew from first principles and landed adjacent to React. Name things accordingly.

If you read the primer, the shape should already feel familiar to anyone with React experience. A page is a tree of components. Each component owns some state, receives some configuration from its parent, and is responsible for rendering itself. When an input changes, a diff flows up, the tree re-renders, and the DOM is updated in place. The mental model transfers almost verbatim.

The engine was not designed to mirror React. It grew from a different set of first principles — HATEOAS affordances, faithful projection, stateless server, self-describing documents — and ended up at a structure that is recognizably React-shaped. Either React solved problems that also exist here, or both systems converged on the same invariants. Both readings are true.

The engine uses the standard vocabulary where the standard vocabulary fits. The base class is Component; each concrete type is TextComponent, PageComponent, NavigationComponent, and so on. Seed constructor arguments are props; Store entries are state; everything else is derived. from_descriptor is reconciliation. Affordance flotation is a portal with a novel merge rule. Faithful projection is the controlled/uncontrolled state boundary applied to an agent-plus-human audience instead of just an in-browser one.

The payoff of using the standard names is cumulative, not dramatic: new contributors search for what they already know. Internal documentation stops inventing local jargon. Design discussions inherit a decade of React community resolution on debates like controlled-vs-uncontrolled, context, and error boundaries. AI agents arriving cold to the codebase are productive faster because they have already read millions of words about the concepts involved.

The rest of this page is the reference: how each React concept is spelled here, what lives where, and which concepts we deliberately don’t borrow.

03 Props, State, Derived

Every component field is one of three things. Misplacing a field is the single most common source of subtle bugs.

The descriptor-as-truth refactor drew React’s most important line: where does this value live? The three categories below each have a canonical location on disk and a mutation API. When adding a new field, pick a category first — the category determines everything else.

Props

parent __structure descriptor

Captured at seed construction, overridable via the descriptor. Mutations flow through _set_my_field (top-level) or _set_my_config (type-specific config). The runtime instance is a projection of the descriptor, not an independent source of truth.

  • label, instruction
  • editable
  • NavigationComponent.mode
  • TextComponent.multiline, min_length, max_length
  • NumberComponent.min_val, max_val

State

Store at key scope

Persisted per instance, per component key, in the instance JSON file. Modifications flow through _handle() during action dispatch. This is what a user’s interactions actually change.

  • TextComponent current text
  • CheckboxComponent selected options
  • NavigationComponent active tab
  • ListComponent ordered items
  • TableComponent row data

Derived

computed each serialize

A pure function of current prop + state (possibly including siblings). Never persisted. Never mutated directly. Recomputed on demand.

  • is_complete
  • has_data
  • ComputedComponent.compute_result
  • ListComponent.effective_must_follow
  • All effective_* properties
The rule: props live in the descriptor, state lives in the Store, neither owns derived values. The category tells you which mutation path to use. See docs/architecture.md §1 for the authoritative spec.

04 Reconciliation

from_descriptor is reconciliation. The alias reconcile is exported at the registry module level for discoverability.

Descriptor tree
from JSON Store
→
from_descriptor
match by key, deepcopy seed, apply overrides, recurse
←
Seed tree
from pages/*.py
↓
Bound component tree
live, serializable, renderable

The shape matches React reconciliation with interesting differences. React diffs two render trees (previous → next) and emits DOM mutations. We diff a descriptor tree against a seed tree and emit a bound Python tree. Both preserve identity via keys. Both are idempotent. Both have a callable-preservation problem.

The callable problem. When a seed contains ComputedComponent(key="score", compute=lambda s: ...), the lambda cannot serialize to JSON. On reconciliation, the descriptor has no compute; only the seed does. If the seed is missing — because the Python definition moved, the key changed, or a sibling was renamed — the callable is silently dropped. The form renders but does nothing. No warning.

What shipped

  • Docstring on from_descriptor names the operation “reconciliation” and lifts the callable-preservation limitation to a first-class Raises block.
  • Module-level alias reconcile = from_descriptor in engine/registry.py. Readers who know the React term find it; readers who know the local term keep working.
  • Typed sibling refs via SiblingRef: a str-subclass value with an optional expects= type assertion, validated at bind time. Stale or type-mismatched references raise SiblingRefError with actionable diagnostics instead of failing silently.

What’s still open

The callable-preservation problem above still has a silent mode. When a seed moves or is renamed and reconciliation falls back to fresh construction, any declared callable-valued field simply returns None. The planned fix is to require the seed parameter when a type declares callable fields and return a typed diagnostic on mismatch so the broken state is visible in the UI. Not yet shipped; tracked as a Pass 2 follow-on.

05 Error boundaries

Rendering failures are scoped, visible, and do not take the whole page down.

A quality system makes failures visible, scoped, and reportable. React error boundaries deliver exactly that shape: a container catches exceptions from its subtree, renders a structured placeholder, lets siblings continue. The engine implements the render-time case today.

Before

A child raises → the whole page 500s.
  • Child render() exception kills the request.
  • Sibling components never render.
  • No diagnostic in the UI.

Now

A child raises → it becomes a visible error card.
  • Component.render_safely() default wraps render() in try/except.
  • Exception → structured card with key, type, exception class, message. Flask debug mode adds a collapsible traceback.
  • Defensive fallback to minimal inline HTML if the _error_boundary.html template itself fails.
  • Siblings render normally; page remains interactive.

The shape

def render_safely(self) -> str:
    try:
        return self.render()
    except Exception as e:
        return _render_error_card(self, e)

# Every container iterates render_safely() on children instead of render().
# Eighteen call sites across ten modules.

Shipped & open

  • Shipped: render-time boundary via Component.render_safely(). Theme-agnostic .c-error-* CSS. Eighteen child-render call sites swapped from render() to render_safely(). Parity tests and backward compatibility unaffected.
  • Parked (follow-ons): serialize_safely() for JSON-side parity; bind() error scoping (the component tree literally does not exist post-bind failure, so there is nothing to contain today); _handle() error scoping around partial-mutation risk.
  • Not yet: a Report affordance that files structured error evidence into the QMS audit log. Small CR when the QMS workflows come online.

06 Context (parked)

The shape is clear. The pain point is not.

React Context solves “an ancestor passes data to a deep descendant without prop-drilling through every intermediate component.” Hypothetical component uses:

Hypothetical use Current state
Passing Store to childrenAlready solved. bind() threads _store.
Passing theme to templatesAlready solved. Thread-local in templates.py plus data-theme attribute.
Passing user / permissionsDoes not exist yet. No authenticated user model.
Passing validation scopeDoes not exist yet. ValidationComponent uses sibling refs.
⏺

Adding a Context primitive today would be speculative generality. Park it. When a concrete pain point arrives — most likely user/permissions once the QMS workflows come online — the shape is clear: a typed provider at the container level, a _context_get(ClassRef) accessor at any descendant depth, validated at bind time like SiblingRef. Half a day of work, delayed until it earns its keep.

07 What we’re not borrowing

Four React concepts that would be bad translations. The common thread: each solves a client-side problem we don’t have.

✕ Hooks

useState, useEffect, useContext exploit JavaScript closure ergonomics and call-order stability. A Python port would be either a fragile call-counter dict or decorator magic. Component subclasses with fields plus descriptors already cover “composable state with identity.”

✕ Functional components

React moved from class components to function components for hook composition. Without hooks, there is no composition benefit. Class-based components are the right shape for this engine.

✕ JSX

Python seed files are our JSX — more honest for being just Python. A Python-embedded DSL would add build complexity for essentially no gain. Jinja2 on the render side is serviceable.

✕ Refs

Refs are an imperative escape hatch to the DOM. This engine has no such escape hatch by design. Actions flow through POST; state flows through Store. Adding refs would break HATEOAS and replayability.

✕ Suspense / Server Components

These solve client-side hydration and streaming problems. Our server is the rendering runtime; there is nothing to hydrate. Not our problem.

What’s still open

The second-order effect

Every AI model has read millions of words about React. None has read this codebase. When the codebase uses React-standard names for React-standard concepts, any agent arriving for the first time is productive faster. The vocabulary itself is a documentation artifact — an invisible alignment between this engine and the broader ecosystem that reads its source.

The architectural investment was already paid. The passes above are harvest, not capital expenditure. The codebase moved from “make it work” to “make it clear” to “name it the same way everyone else does.”
