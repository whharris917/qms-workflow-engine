Razem

A hypothetical encyclopedia entry about the Razem framework, written in the style of a Wikipedia article.

Razem (Polish: together) is a Python framework for building interactive applications that serve humans and artificial-intelligence (AI) agents from a single source definition. Developed under the Pipe Dream project as the runtime for a GMP-inspired Quality Management System, it treats a web page and a machine-readable API as two projections of the same underlying state, an invariant the project refers to as faithful projection.[1] Razem uses a component tree as its primary abstraction, reaching a design recognizably adjacent to React and similar front-end libraries despite being developed from different first principles.[2]

Razem is notable for making AI agents a first-class client: every rendered button corresponds to a machine-readable affordance exposed at the same HATEOAS URL, enabling a language model to drive any workflow without a parallel API schema.[3] The alignment between the two surfaces is enforced at continuous-integration time by a parity test suite.[4]

Although Razem grew out of work on a quality management system, the framework itself contains no QMS-specific code and is general-purpose. The QMS it serves — internally the QMS Workflow Engine — is the first intended application to be built on top of Razem; the two had been conflated under a single name for most of early development before being disentangled.[13]

Initial development began in early 2026 as a clean-room rebuild of an earlier CLI-based workflow engine. The current architecture is the fourth major iteration.[5]

History

Razem originated as part of Pipe Dream, a project combining a Python-based quality management system with a downstream application called Flow State. The QMS was initially bootstrapped with a command-line interface for document control (change records, investigations, variance reports) but lacked a runtime for the actual workflows the QMS described.[5]

A first workflow engine, based on YAML definitions and graph traversal, was prototyped in March 2026 (known internally as “Workflow Engine v1”). A web-based iteration followed (v2), which split handler logic across multiple implementations. In late March 2026 the codebase was deleted and rebuilt from first principles around a new abstraction the developers called the eigenform: a self-contained unit that rendered itself to HTML, serialized itself to JSON, and dispatched its own actions.[5]

The eigenform name, originally intended to evoke the eigenvector sense of “preserves identity under transformation,” was retired in April 2026 in favor of the industry-standard term component.[6] The project team described the original name as a path-dependent choice that obscured the architecture’s fundamental similarity to existing component frameworks.[2]

Subsequent development focused on four “framing passes” aligning the framework’s vocabulary with React conventions: naming internal invariants (props, state, derived; reconciliation), adding typed sibling references with bind-time validation, introducing render-time error boundaries, and finally renaming the base class from Eigenform to Component.[1]

Later in April 2026, the framework itself was renamed. Until that point the codebase had been referred to interchangeably as the “QMS Workflow Engine,” conflating the framework with its first intended application. Recognizing the naming equivalent of describing React as “Facebook JS,” the project team separated the two identities: the framework was renamed Razem (Polish for “together”), reflecting the dual-audience invariant that humans and AI agents together read the same self-describing page. The name QMS Workflow Engine was retained for the application under construction.[13]

Architecture

The core loop

Every request processed by Razem walks four stages:[7]

  1. Define. Page definitions live as Python modules in pages/, auto-discovered on every request. A definition exports a seed: an unbound tree of component instances.
  2. Bind. The server attaches a per-instance JSON file called the Store to the seed, producing a live, scoped, Store-connected tree.
  3. Serve. The bound tree serializes to JSON (for agent clients) or renders to HTML (for browsers). Both outputs describe the same state and expose the same URLs.
  4. Handle. On a POST, the server rebinds, walks to the target component by URL path, and invokes its _handle() method, which validates the body, writes to the Store, and returns the updated state.

The server holds no long-lived component tree in memory; every request rebuilds the tree from the seed plus the Store. Because the Store is the only authoritative mutable state, the engine is trivially horizontally scalable: any server can handle any request, and editing a page definition takes effect on the next request with no restart.[7]

Seed, descriptor, and bound tree

Three related trees participate in rendering any page:[8]

  • The seed tree is the Python definition in pages/*.py. Immutable, holds callables (lambdas, validators, compute functions), has no identity.
  • The descriptor tree is a JSON-serializable snapshot stored in the Store at __structure keys. It is the canonical source of truth for any runtime-editable structure.
  • The bound tree is the live, scoped instance tree the engine renders and serializes. Rebuilt every request.

The operation that produces the bound tree from a seed plus a descriptor is called reconciliation, and is exposed under both names (from_descriptor and reconcile) for discoverability. It walks the descriptor, matches each node against the seed by key, deepcopies the matched seed to preserve callables, and applies the descriptor’s scalar overrides on top.[8]

Affordances and HATEOAS

Every component’s JSON serialization includes a list of affordances: dicts describing the actions currently available, with label, HTTP method, URL, POST-body template, and a natural-language instruction. Both browsers and agents consume affordances directly — browsers render them as buttons, agents interpolate values into the body template and POST.[3]

This is the HATEOAS principle applied consistently: the server’s response describes the actions available next, so no out-of-band API schema is required. An AI agent interacting with the engine can walk any workflow by reading each response and picking an affordance to follow, without holding a separate specification.[3]

Features

Component types

See also: Component Reference.

Razem ships with 26 built-in component classes registered under 31 names, covering data leaves (TextComponent, NumberComponent, DateComponent, BooleanComponent, ChoiceComponent, CheckboxComponent, MultiComponent), collections (ListComponent, SetComponent, DictionaryComponent, TableComponent), containers (PageComponent, GroupComponent, NavigationComponent, RepeaterComponent), reactive components (SwitchComponent, VisibilityComponent, DynamicChoiceComponent, ComputedComponent, ScoreComponent, ValidationComponent), and wrappers (HistoryComponent, ActionComponent, InfoComponent).[9]

A single NavigationComponent class replaces what other frameworks expose as four separate widgets (tabs, wizards, sequences, accordions), switching behavior via a mode prop that accepts one of four literal values.[9]

Faithful projection

Faithful projection is Razem’s term for the invariant that JSON and HTML views of a page describe the same state and expose the same URL surface. The property is enforced at continuous-integration time by a 72-test parity suite spanning nine test categories, including forward parity (every JSON URL appears in HTML), reverse parity (every clickable HTML URL is declared in JSON), action-name parity, URL resolvability, and structural shape tests.[4]

Affordance flotation

Affordances marked _floatable by a component serialize through the tree and surface at the top-level PageComponent, collapsed into a single parameterized compound affordance with a structured targets dictionary. The mechanism is conceptually similar to React’s createPortal, though applied to machine-readable JSON rather than DOM placement, and with a novel merge step that groups affordances of the same action kind together.[10]

Flotation reduces the size of agent-facing JSON without affecting HTML rendering. On flat pages, affordance count drops by roughly 61%; on deeply nested pages the savings are larger.[10]

Mutable pages

Pages declared with mutable_structure=True permit runtime editing of the component tree itself, including adding, removing, moving, reparenting, and grouping children. Edits persist to the page’s __structure descriptor and survive restarts. The feature is exposed to both human users (via a tile-based structural editor and drag-and-drop) and to AI agents (via a documented action protocol with actions named add_component, remove_component, move_component, reparent_component, group_components, ungroup_component, and rebuild_from_seed).[11]

Components of type ActionComponent can additionally return structural_actions from their handlers, enabling self-modifying pages in which the tree reshapes itself in response to user interaction. This capability was introduced under the internal name “fractal complexity plan” in March 2026.[5]

Error boundaries

As of April 2026, the base Component class implements render_safely(), which wraps render() in a try/except and returns a structured error card on failure. Eighteen child-render call sites across ten component modules delegate to render_safely() so a single component’s rendering exception does not take the whole page down. The error card is theme-aware and includes an optional Python traceback in Flask debug mode.[1]

Design philosophy

Razem was designed around two principles described in the project’s architectural documentation:[2][12]

  • Dual-consumer equivalence. Human operators and AI agents interact with the same URL, take the same actions against the same endpoints, and see equivalent representations of the same state. Neither surface is a second-class citizen.
  • Stateless server authority. The server holds no in-memory component tree between requests. The Store JSON file is the sole source of truth; every request rebuilds the tree from a seed plus the Store.

The project’s self-analysis document observes that the design landed “closer to React than anyone planned,” despite emerging from independent first principles (HATEOAS, content negotiation, faithful projection, stateless server, self-describing documents).[1] The developers describe this convergence as either evidence that React solves problems common to any component-based interactive application, or that both systems converged on shared invariants from distinct starting points.[1]

Terminology

Affordance
A dict describing an available action, with label, method, URL, body template, and instruction. Plural affordances. A component’s serialization includes its current affordance list.
Bind
The operation that attaches a Store to a seed and produces a live tree. Analogous to React’s component mount.
Component
Razem’s base abstraction, previously called an eigenform. Each concrete component is a Python dataclass subclass (TextComponent, NavigationComponent, etc.) implementing the protocol: serialize(), render(), _handle().
Descriptor
A JSON-serializable snapshot of a component tree, stored at the __structure key inside the Store. Canonical source of truth for structure and props.
Faithful projection
The invariant that HTML and JSON views of a page expose the same URL surface and describe the same state. Enforced by parity tests.
Reconciliation
The operation that builds a live component tree from a descriptor plus a seed. Implemented by the from_descriptor function (aliased as reconcile).
Seed
The unbound Python definition of a page. Lives in pages/*.py as a module-level definition variable.
Store
The per-instance JSON file holding all mutable state for a page instance. One file per instance at data/{instance_id}.json.

The closest analogue in spirit is Phoenix LiveView — both systems maintain server-authoritative component state, use morphdom-style DOM diffing, and eschew client-side hydration. Unlike LiveView, Razem treats machine agents as a peer client rather than a consumer of a separate API, and its state lives in per-instance JSON rather than in-memory server processes.[2]

Limitations

The project’s self-analysis document (Deep Dive) enumerates several acknowledged gaps:[12]

  • Unstructured action dispatch. The engine has 88 if action == "..." branches across 20 files, implementing what amounts to a Redux-style reducer pattern without the name or an explicit registry. A formal action registry is on the backlog.
  • Silent callable-preservation failure. When a seed is renamed or deleted and reconciliation falls back to fresh construction, components with callable-valued fields (ComputedComponent.compute, DynamicChoiceComponent.options_fn) silently receive None. The fix requires the seed parameter when callable fields are declared, with a typed diagnostic on mismatch.
  • No Context primitive. The engine has no ancestor-to-descendant data channel equivalent to React Context. Sibling references exist but propagate only laterally. A Context primitive has been considered and explicitly parked until a concrete use case arrives.
  • No concurrency model. Two simultaneous writers to the same component produce last-write-wins. The Store uses atomic write-temp-then-rename on every write, but there is no optimistic concurrency or conflict detection.
