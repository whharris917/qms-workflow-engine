What is an Element?

A workflow is a sequence of nodes. Each node presents the user (human or agent) with things to read and things to do. Those things are elements — the atomic building blocks of every workflow page.

An element is anything that occupies space in a node's content area: a text field to fill in, a yes/no toggle, a selection from a list of options, a read-only indicator, a group of related fields, a table, or a managed list. The engine does not distinguish between "inputs" and "displays" — they are all elements, differing only in type and in whether they generate affordances.

Three representations

Every element exists in three forms simultaneously. Understanding these three representations is the key to understanding the engine.

1. Definition (YAML)

The workflow author declares elements in YAML. This is the source of truth — it defines the element's type, label, instruction text, options, visibility rules, and side effects. The engine reads this once at load time and never modifies it. 

fields:
  title:
    label: Document Title
    type: text
    instruction: A short, descriptive title.
2. State + Affordances (JSON)

At runtime, the engine projects the definition into a canonical response: the element's current state (its value, label, visibility) and its affordances (what actions are currently possible). This is what an agent receives from GET /agent/{id}/{inst}. The two are always delivered together — an agent never sees state without knowing what it can do. 

// state — in the content array
{"type": "text", "label": "Document Title", "value": null,
 "instruction": "A short, descriptive title."}

// affordance — in the affordances array
{"id": 1, "label": "Set Document Title",
 "method": "POST", "params": {"value": "(text)"}}
3. Rendered (UI)

The human renderer projects the same state and affordances into interactive HTML. Every visible control traces back to an affordance; every affordance has a corresponding control. This is the faithful projection principle — the human view and the agent view are two lenses on the same data, never diverging.

The content array

A node's elements are delivered as an ordered content array in the state response. Each item carries its own type field, so the renderer can dispatch without any external schema. The order of items in the array matches the order declared in the YAML definition — what you write is what the user sees. 

// GET response → state.content
[
  {"type": "group", "label": "Basic Information", "fields": [...]},
  {"type": "toggle", "label": "Affects Code", "value": false},
  {"type": "choice", "label": "Priority", "value": null, "options": ["Low", "Medium", "High"]}
]
Element taxonomy

Seven element types, organized by role:

CategoryTypesRole
leaf element text, toggle, choice, indicator Single values. Each generates one affordance (except indicator, which is read-only).
container group Bundles multiple leaf fields under a single set_fields affordance, reducing agent round-trips.
structural table, list Multi-row data structures with their own operation vocabularies.

Elements can also have behavioral features layered on top: visible_when hides an element until a condition is met, side_effects auto-sets other fields when a value changes, and default provides an initial value. These are not element types — they are properties that any leaf element can carry.

Explore each type below — click a tab to see its YAML definition, live agent view, and interactive rendered form. Every demo on this page is driven by the same renderer code that runs in production.

indicator
leaf element

  type: indicator   # legacy: computed
  compute:
    fn: all_set
    args: [title, category, priority]
  instruction_when_true: All required fields are set.
  instruction_when_false: Please complete all required fields.

visible_when
behavioral

  
A field-level predicate that hides the field (and its affordance) until the condition is met. Hidden fields are absent from the content array entirely — the agent cannot accidentally set them. Set Code Impact below to reveal the Submodule field.

  
YAML definition

  
fields:
  affects_code:
    label: Code Impact
    type: toggle
    instruction: Does this change affect code?

  submodule:
    label: Submodule
    type: choice
    options: [flow-state, qms-cli, qms-workflow-engine]
    instruction: Which submodule is affected?
    visible_when:              # legacy: {field_key: expected_value} — all pairs ANDed
      affects_code: true       # hidden until affects_code == true

  sdlc_governed:
    label: SDLC Governed
    type: indicator
    visible_when:              # modern expression tree format:
      op: AND
      conditions:
        - { type: field_equals, key: affects_code, value: true }
        - { type: field_not_null, key: submodule }

  
Agent view

  

  
Rendered

  

  
Notes:
    
    
      
  • Hidden fields are absent from the content array — not just greyed out
    • 
      
  • Hidden fields also emit no affordance — cannot be set while invisible
    • 
      
  • Legacy format: { key: expected_value } — all pairs must match (implicit AND); use not_null as a sentinel value to match any non-null
    • 
      
  • Modern format: full expression tree — supports AND/OR/NOT and all leaf condition types (see Expression Language)
    • 
    

  







  
side_effects
behavioral

  
A field-level list of conditional writes. When the field is set, each when condition is evaluated against the new state; matching entries immediately write their set dict into workflow state. The agent takes one action; the cascade happens automatically. Set Category to Security or Data below to trigger a compliance flag.

  
YAML definition

  
fields:
  category:
    label: Category
    type: choice
    options: [Software, Hardware, Process, Security, Data]
    instruction: Primary category of this change.
    side_effects:
      - when:
          op: OR
          conditions:
            - { type: field_equals, key: category, value: Security }
            - { type: field_equals, key: category, value: Data }
        set:
          requires_compliance: true
      - when:
          op: NOT
          conditions:
            - op: OR
              conditions:
                - { type: field_equals, key: category, value: Security }
                - { type: field_equals, key: category, value: Data }
        set:
          requires_compliance: null

  
Agent view

  

  
Rendered

  

  
Notes:
    
    
      
  • All side effects are evaluated in order; multiple may match and all are applied
    • 
      
  • Side effects are evaluated after the triggering field is written, so conditions may reference the new value
    • 
      
  • The set dict can write any key in workflow state — including keys from other nodes
    • 
      
  • Commonly used to set derived flags (compliance requirements, routing hints, pre-populated defaults)
    • 
      
  • Side effects are invisible to the agent — the updated keys simply appear in subsequent state reads
    • 
    

  







  
proceed
flow control

  
A gated navigation affordance that advances the workflow to the next node. The proceed affordance only appears in the agent's affordance list when the optional gate expression evaluates to true. Fill both fields below to unlock the button.

  
YAML definition

  
nodes:
  initiation:
    title: Initiation
    instruction: Fill in the required fields before proceeding.
    fields:
      title:  { label: Title,   type: text, instruction: ... }
      purpose: { label: Purpose, type: text, instruction: ... }
    proceed:
      label: Proceed to Change Definition
      gate:                                 # omit gate = always available
        op: AND
        conditions:
          - { type: field_not_null, key: title }
          - { type: field_not_null, key: purpose }
      target: definition                    # optional — defaults to next sequential node

  
Agent view

  

  
Rendered

  

  
Notes:
    
    
      
  • When the gate is unmet, the proceed affordance is absent — not just disabled
    • 
      
  • Proceed affordance body: {} normally; {"target": "node_id"} when target: is set
    • 
      
  • Mutually exclusive with fork and router — a node has at most one flow-control primitive
    • 
      
  • Pair with an indicator element to surface readiness feedback while the gate is unmet
    • 
    

  







  
navigation
flow control

  
Node-level affordances for moving between nodes without triggering the proceed gate. navigation entries cover backward/lateral movement; actions cover terminal operations. Both render after content elements and before the proceed/fork affordance.

  
YAML definition

  
nodes:
  definition:
    title: Change Definition
    instruction: Define the scope and impact of this change.
    navigation:
      - action: go_back
        label: Go back to Initiation
      - action: go_to
        label: Jump to Review
        node: review                   # required for go_to
        when:                          # optional guard — affordance suppressed if false
          type: field_not_null
          key: title
    actions:
      - action: submit
        label: Submit for Review       # always emitted, regardless of state
      - action: restart
        label: Restart Workflow

  
Affordance shapes

  

    
TypeURLBodyNotes

    
      
go_backPOST /agent/{wf}/go_back{}Returns to previous node in history stack

      
go_toPOST /agent/{wf}/go_to{"node": "node_id"}Jumps to named node; requires node: in YAML

      
submitPOST /agent/{wf}/submit{}Terminal — closes the workflow instance

      
restartPOST /agent/{wf}/restart{}Resets all state and returns to the first node

    
  

  
Notes:
    
    
      
  • go_back and go_to are declared under navigation:; terminal operations are under actions:
    • 
      
  • Navigation entries with a when guard are only emitted when the guard passes — the agent sees no affordance when the guard fails
    • 
      
  • go_to can target any node by ID, including earlier nodes; useful for correction flows
    • 
      
  • actions are always emitted regardless of any state condition
    • 
    

  







  
Expression Language
reference

  
All conditions in the engine — proceed gates, visible_when predicates, side_effects guards, and navigation guards — use the same expression tree. An empty or absent expression is always true. Unknown types fail closed (false).


  
Composite operators

  
{ op: AND, conditions: [...] }   # true iff ALL conditions pass
{ op: OR,  conditions: [...] }   # true iff ANY condition passes
{ op: NOT, conditions: [expr] }  # true iff the single condition FAILS


  
Leaf condition types

  

    
typeAdditional keysPasses when…

    
      
field_truthykeyValue is truthy (non-null, non-empty string, non-false)

      
field_not_nullkeyValue is not null

      
field_equalskey, valueValue exactly equals value

      
set_membershipkey, set_refValue is a member of the named option_sets entry

      
table_has_columns—Table has at least one column defined

      
table_has_rows—Table has at least one row

    
  


  
visible_when legacy format

  
visible_when:
  affects_code: true   # field_equals — all pairs ANDed; cannot express OR or NOT
  submodule: not_null  # special sentinel for field_not_null


  
indicator compute functions (compute.fn)

  

    
fnAdditional keysTrue when…

    
      
all_setargs: [key, ...]All listed keys are non-null

      
any_setargs: [key, ...]At least one listed key is non-null

      
equalskey, valueNamed key exactly equals value

      
not_equalskey, valueNamed key does not equal value

    
  


  
Example: compound gate

  
proceed:
  label: Proceed to Review
  gate:
    op: AND
    conditions:
      - { type: field_not_null, key: title }
      - op: OR
        conditions:
          - { type: field_equals, key: risk_level, value: Low }
          - { type: field_not_null, key: risk_justification }


  
Notes:
    
    
      
  • Expressions are evaluated against the live workflow state dict at the moment the affordance list is requested
    • 
      
  • provider_state is an additional leaf type for external state integrations (not commonly needed)
    • 
      
  • The evaluator returns (passed: bool, reason: str) — the reason string is available in server logs for debugging
