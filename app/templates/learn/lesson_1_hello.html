The smallest interactive page

Here is a complete page definition. One file, eight lines, a fully working interactive form. 

# pages/hello.py
from engine.page import Page
from engine.textform import TextForm

definition = Page(
    key="hello",
    label="Hello Page",
    components=[
        TextForm(label="Your name"),
    ],
)

Save that as pages/hello.py. Start the server with python run.py. Open the Agent Portal, click “New” next to the Hello Page card, and you’ll be looking at your first running page. The URL will be something like /pages/a3f9c2d1 — each spawned instance gets its own 8-character hex identifier.

No HTML, no JSON schema, no route declaration. The page was defined — the engine handles rendering, routing, serialization, and persistence. This is the shape of every page.

What you just built

Two Python imports, two class instantiations. Let’s name what each piece is.

  • Page — the top-level container. Every page starts with one. It owns the Store (the JSON file where this page’s state lives) and hands it down to children.
  • TextForm — a single text input. The only required argument is label (what humans see). Optional configuration includes multiline, min_length, and an explicit key= — see “When keys matter” below.
  • components=[...] — the container’s children. Add more TextForms, or other component types, and they appear in the rendered page in order.

The variable must be named definition. The engine auto-discovers every file in pages/ and looks for that name. The file’s key ("hello") becomes the seed identifier in the Agent Portal.

See it both ways

With the page open in your browser, you’ve already seen the HTML view. To see the JSON view, the easiest path is curl from another terminal. The engine serves JSON by default — HTML is only returned when the request explicitly asks for it with Accept: text/html (which browsers always send, and curl never does): 

# Human view — what your browser gets (explicit Accept)
curl -H "Accept: text/html" http://127.0.0.1:5000/pages/a3f9c2d1

# Agent view — the engine's default, no header needed
curl http://127.0.0.1:5000/pages/a3f9c2d1

The agent view comes back as structured JSON — the same state the browser rendered, but every interactive element is listed as an affordance with its method, URL, and body shape. For the two-component page above (TextForm + CheckboxForm), the response looks like this:

Things to notice:

  • Every form and button a human can click shows up as an affordance with the exact URL and body shape an agent would POST. There is no separate API schema — the schema is the response.
  • The auto-generated keys (text-b72b50fa, checkbox-70b15c71) appear in the affordance URLs. They’ll differ on your machine — each instance gets its own.
  • The page-level URL (/pages/a3f9c2d1) and component paths (/pages/a3f9c2d1/text-b72b50fa) mirror the tree structure.

Same URL. Different response shape. Same state. This is the property that makes the engine different from a typical web framework: one definition produces two surfaces, and they agree on every action you can take. Lesson 5 covers why that matters.

Try it. Type a name into the field and click “Save”. The value is persisted to data/a3f9c2d1.json. Refresh the page — your name is still there. Reload the server — still there. The engine is stateless in memory; the Store is the source of truth.

A small addition

One more component, one more line. Add a checkbox for preferences: 

# pages/hello.py
from engine.page import Page
from engine.textform import TextForm
from engine.checkboxform import CheckboxForm

definition = Page(
    key="hello",
    label="Hello Page",
    components=[
        TextForm(label="Your name"),
        CheckboxForm(
            label="Preferences",
            items=["Email me", "Follow updates", "Send notifications"],
        ),
    ],
)

Save. Reload the page in your browser (no server restart needed — pages/ is auto-discovered every request). The checkbox appears. Each component is isolated: changing one doesn’t affect the other. Each one persists its own state under its own key in the Store.

Extracting children for legibility

The definition grows with every component you add. At some point it’s clearer to lift children into named variables and reference them in the components list: 

# pages/hello.py
from engine.page import Page
from engine.textform import TextForm
from engine.checkboxform import CheckboxForm

name = TextForm(label="Your name")

preferences = CheckboxForm(
    label="Preferences",
    options=["Email me", "Follow updates", "Send notifications"],
)

definition = Page(
    key="hello",
    label="Hello Page",
    components=[name, preferences],
)

Functionally identical — the variables are just handles for readability. This pays off once children have long configurations, once you want to group related definitions in the source, or once you start composing components into larger trees (Lesson 4).

When keys matter

Notice that none of the child components above pass an explicit key=. When you omit one, the engine generates a stable identifier like text-a3f9b2c1 at construction time — unique per component, preserved across deepcopy and server restart, and visible as the URL path segment for that component. For most cases that is enough.

You want to specify a key explicitly in two situations:

  • Stable URLs. With an auto-generated key, the component’s URL is /pages/{id}/text-a3f9b2c1. If you want /pages/{id}/name instead — for documentation, external links, or a curl script that has to keep working across edits — pass key="name".
  • Cross-component references. Several component types react to a sibling by name (Visibility, Switch, Computation, and others use a string key to find their target). Those references need the target to have a stable, meaningful key. Lessons 4 and 7 cover this in detail.
# Explicit key — URL becomes /pages/{id}/name, and siblings can reference "name"
TextForm(key="name", label="Your name")

The rule of thumb: give your Page an explicit key — it’s the seed identifier in the Agent Portal and in instances.json, and a meaningful name there beats page-a3f9b2c1. Child components can go unnamed until a stable URL or a sibling reference requires a specific name.

What you learned

  • Core A page is a Python file in pages/ exporting definition = Page(...).
  • Core The engine auto-discovers pages, routes requests, renders HTML and JSON, and persists state — you just describe the tree.
  • Core Every component has a key (auto-generated unless explicit) that identifies it within its container. For child components the key is also the URL path segment; for a Page it’s the seed identifier in the Agent Portal — running instances get their own auto-generated ID in the URL.
  • Tip Specify an explicit key= when you need a stable URL or when a sibling component will reference it by name; otherwise let the engine generate one.
  • Tip Page state lives in data/{instance_id}.json. You can inspect it or delete it to reset.
