The three categories

If you’ve used React, this will feel familiar — the engine uses the same three-way split. Every field on every component is exactly one of:

  • Props — configuration from the parent. Label, instruction, min/max, mode.
  • State — the value the user changes. Current text, selected options, active tab.
  • Derived — computed from props + state. Completeness, validation result, derived totals.

Misplacing a field into the wrong category is the single most common source of subtle bugs. The good news is that the category tells you where the value lives, which mutation API to use, and whether the field survives various lifecycle events. Once the category is right, everything else falls out.

Props — in the parent's descriptor

A prop is a configuration value set at seed-construction time, overridable later via the parent container’s __structure descriptor entry for this child. 

# Props are passed as keyword arguments at seed time
TextForm(
    key="name",
    label="Your name",         # prop
    instruction="First and last", # prop
    multiline=False,            # prop
    min_length=2,                # prop
    max_length=100,              # prop
)

Where does the label actually live? Inside the parent Page’s Store entry at __structure, in the descriptor entry for this child. The runtime TextForm instance is a projection of that descriptor — not an independent source of truth.

That matters because the parent can override a prop at runtime. Edit mode lets a user rename a label, adjust min_length, flip multiline. Those changes flow through _set_my_field() (for top-level fields like label) or _set_my_config() (for type-specific config like multiline) — each writes back to the parent descriptor. 

# Not "the component mutates itself" — the parent descriptor changes.
self._set_my_field("label", "Full name")     # update top-level prop
self._set_my_config("multiline", True)          # update config prop
Rule of thumb. If a field is declared in the component’s @dataclass and its value survives across requests because the container re-applies it on bind, it’s a prop.

State — in the Store at key scope

State is the mutable content the component owns directly. It’s what the user changes. It’s persisted per instance, per component key, in the Store JSON file. 

# Example Store file: data/a3f9c2d1.json
{
  "hello": {
    "__structure": { /* props live here */ },
    "name": { "value": "Alex" },                // TextForm state
    "preferences": { "selected": ["Email me"] } // CheckboxForm state
  }
}

Each component reads from and writes to its scoped entry. The scope is the parent’s key (here, hello) and the component’s own key is the inner dictionary key (name, preferences).

Mutations happen through the component’s handle() method, which dispatches through the class’s _actions registry to a handler method. TextForm maps set_value and clear to their respective handlers; CheckboxForm maps toggle_option and done. Each handler parses the POST body, validates, writes to the Store, and returns the updated state.

Rule of thumb. If a field’s value changes because the user did something, it’s state.

Derived — computed on each serialize

Derived values are pure functions of the current prop + state pair (possibly including siblings). Never persisted. Never mutated directly. Recomputed every time the component serializes or renders. 

# Example: is_complete is derived — always computed, never stored
class TextForm(Component):

    @property
    def is_complete(self) -> bool:
        value = self._store.get(self._scope, self.key, "value")
        if not value:
            return False
        if self.min_length:
            return len(value) >= self.min_length
        return True

Why not cache is_complete? Because then you’d need to invalidate it every time state or props change — and cache invalidation is famously hard. Recomputing on demand is cheap (it’s a dict lookup and a length check) and always correct.

Other examples of derived values in the engine:

  • has_data — “does this component have anything to clear?”
  • Computation.compute_result — runs a user-supplied function against sibling values (the graded() helper in engine/helpers.py is a thin wrapper for the answer-key quiz-grading case)
  • Validation rule pass/fail
  • ChoiceForm.options when declared as a SiblingBind — which options are available based on a sibling’s value
Rule of thumb. If you can compute the value at serialize-time from other values, it’s derived. Don’t cache it. Don’t persist it. Recompute.

The invariant

Props live in the descriptor. State lives in the Store. Neither owns derived values.

Every field addition has to pick a category. The category determines:

  • Where the value lives on disk
  • Which mutation API to use (_set_my_field / _set_my_config / _handle)
  • Whether the field is reconstructed on reconciliation
  • Whether the field survives a seed change

When in doubt, ask: what changes this value?

  • Seed definitions → prop
  • User actions → state
  • Other values → derived

A concrete example

Say you’re adding a placeholder field to TextForm. Which category? Work through the rule:

  • It’s declared at construction time with a default. → prop
  • The user doesn’t type it; the page author sets it. → prop
  • It should survive a reload, because it’s part of the page definition. → prop

So: add it as a dataclass field on TextForm. That puts it in the descriptor. No Store entry needed. No mutation API needed beyond _set_my_config("placeholder", ...) if you want to edit it at runtime.

Contrast with “draft_value — the user is typing but hasn’t submitted yet.” That’s state if it survives navigation; it’s uncontrolled (client-only) state if it doesn’t. Lesson 5 covers the controlled/uncontrolled boundary.

What you learned

  • Core Every field is prop, state, or derived — never a mix.
  • Core Props live in the parent descriptor; state lives in the Store; derived is recomputed on each serialize.
  • Core Pick the category before writing code. It tells you everything else.
