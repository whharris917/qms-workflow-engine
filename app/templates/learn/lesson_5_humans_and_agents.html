Two clients, one definition

The engine was built for a specific pain: AI agents and human operators need to interact with the same workflows, and historically this required maintaining two separate surfaces — a styled web UI and a JSON API — that drift apart over time.

The engine collapses these into one definition. A single Python file produces a page that a browser renders as HTML and an agent consumes as JSON. The two views describe the same state. The two clients take the same actions against the same URLs. When the definition changes, both views update.

This lesson explains three ideas that make this work: affordances, HATEOAS, and faithful projection.

Affordances — what the client can do right now

An affordance is a description of an available action. Every component emits a list of them as part of its serialization: 

# An affordance is just a dict. Serialized form:
{
  "label": "Save",
  "method": "POST",
  "url": "/pages/hello-1/name",
  "body": {"action": "set_value", "value": "<value>"},
  "instruction": "Submit the text value. Must be at least 2 characters."
}

Four fields do the work:

  • label — human-readable name (for buttons)
  • url — where to POST (or GET)
  • body — the POST body shape, with placeholders like <value>
  • instruction — natural-language guidance for an agent reading this

A browser renders the affordance as a button that POSTs the body on click. An agent reads the same affordance, interpolates its value into the placeholder, and POSTs. Same URL, same body shape, same result.

HATEOAS — the server tells you what you can do

HATEOAS (Hypermedia As The Engine Of Application State) is a REST design principle: the server’s response tells the client what actions are available next. The client doesn’t need an external schema; it discovers the API by reading each response.

In practice, this means an agent interacting with the engine never needs a separate API doc. For every component, the JSON response contains:

  1. The current state (values, completeness, configuration)
  2. The list of affordances describing every action available at this moment

The agent picks an affordance, follows its URL, POSTs the body, and receives a new response with a new set of affordances describing what’s now possible. The workflow emerges from affordance-following, not from pre-coded paths. 

# An agent's loop, in pseudocode
response = GET("/pages/survey-1")
while not response["is_complete"]:
    affordances = collect_affordances(response)
    chosen = pick_best(affordances)        # LLM judgment
    body = fill_template(chosen["body"])     # interpolate placeholders
    response = POST(chosen["url"], body)

No external schema, no hard-coded endpoint list, no parallel documentation. The API is the affordances.

Compare to typical REST. Most REST APIs require an out-of-band OpenAPI / JSON Schema document to describe endpoints. An agent has to download the schema, reconcile it with response shapes, maintain client code per endpoint. HATEOAS removes the middleman: the response tells you what to do next.

Faithful projection — HTML and JSON describe the same state

Affordances only work as a common interface if both surfaces are honest. If the JSON reports an action the HTML doesn’t render (or vice versa), the human and the agent see different applications.

Faithful projection is the invariant that prevents this drift: every affordance in the JSON corresponds to a clickable element in the HTML, and vice versa. It is enforced at CI time by a parity test that iterates every page and diffs the two surfaces. 

# tests/test_parity.py — sketch
def test_affordance_parity(page):
    json_urls = extract_urls(page.serialize())
    html_urls = extract_urls(page.render())
    assert json_urls == html_urls

There’s more nuance — some affordances deliberately surface only in JSON (“compound” affordances that bundle many targets, the equivalent of a React portal), and browser-only UI chrome is exempt — but the core rule stands: if an agent can see an action, a human can reach it through the UI, and vice versa.

Controlled vs uncontrolled state

One more axis of the human/agent split: which state is shared, and which is browser-only?

Controlled state is server-owned. It lives in the Store, round-trips through serialization, appears identically in JSON and HTML. All component values (text, selections, active tabs) are controlled. Both the human and the agent can read and modify them.

Uncontrolled state is browser-owned. It never touches the server. Input focus, scroll position, in-progress text the user is typing, open <details> tags — all uncontrolled. An agent cannot observe them, and that’s fine: they’re presentation-layer concerns, not part of the document state.

Uncontrolled state is preserved across POSTs by morphdom, which diffs the old DOM against the server’s new HTML and mutates only what changed. Focus stays in the input you were typing in; scroll position doesn’t jump; open disclosures stay open. The server doesn’t have to know about any of this.

Don’t break the boundary. If you find yourself wanting to store scroll position in the Store, or wanting the agent to observe focus — stop. That’s presentation state, not document state. Keep it client-side. Conversely, if you want browser-only “draft” values that survive a page reload — don’t cache them in JS; submit them; let the Store own them.

See it work

Try it. Open any page in the engine (say, /pages/your-hello-instance). Then hit the same URL with curl -H "Accept: application/json". You’ll see the JSON version — same state, same URLs, affordances as structured data instead of rendered buttons. Every action the buttons would fire is listed as an affordance you could POST.

Why this matters

Every framework has buttons. Not every framework lets an AI agent drive the application through the same interface a human uses. The engine was built for the case where that agent is a first-class client — not a thing grafted on via a second API.

The consequences ripple outward: workflows are documented by the affordances they expose, not by parallel schemas. Tests exercise real URLs, not mock endpoints. Onboarding a new agent means giving it access to a URL, not writing SDK code. The same page is a browser form, a CLI via curl, and an agent-driven workflow — from one Python file.

What you learned

  • Core An affordance is a dict describing one action: label, URL, body template, instruction.
  • Core HATEOAS: every response contains the affordances describing what’s possible next. No external schema needed.
  • Core Faithful projection: JSON and HTML describe the same state, enforced by parity tests.
  • Core Controlled state lives in the Store and round-trips. Uncontrolled state (focus, scroll) stays in the browser and is preserved by morphdom.
