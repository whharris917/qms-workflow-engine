Containers hold children

Every component is either a leaf (a single input like TextForm) or a container (Page, Navigation, Group, Repeater, Switch). Containers hold other components and delegate behavior down the tree.

The simplest container is Page — which you already used. It takes a components=[...] argument: a list of children rendered in order. That’s the whole API.

Navigation — tabs, wizards, sequences, accordions

The most common non-page container is Navigation. It unifies what other frameworks split into four separate widgets:

  • mode="tabs" — free-access tabs, one visible at a time
  • mode="chain" — gated wizard, each step unlocks the next, auto-advance on completion
  • mode="sequence" — gated wizard with manual Back/Next buttons
  • mode="accordion" — all sections visible with expand/collapse

Same class, four behaviors, set by a single prop. The child shape is the same in all cases: a list of components passed as steps=[...]. 

# pages/survey.py
from engine.page import Page
from engine.navigation import Navigation
from engine.textform import TextForm
from engine.choiceform import ChoiceForm
from engine.booleanform import BooleanForm

definition = Page(
    key="survey",
    label="Quick Survey",
    components=[
        Navigation(
            key="tabs",
            mode="tabs",
            steps=[
                TextForm(key="name", label="Name"),
                ChoiceForm(
                    key="role", label="Role",
                    options=["Engineer", "Designer", "PM", "Other"],
                ),
                BooleanForm(
                    key="subscribe", label="Subscribe to updates?",
                ),
            ],
        ),
    ],
)

Save as pages/survey.py, spawn an instance from the Agent Portal, and you’ll have a three-tab page. Clicking between tabs just flips the active-tab state; each tab’s content stays filled in.

Keys and scope

Every component has a key — a string identifier unique within its containing scope. Keys are how the engine routes requests, how components find their own state in the Store, and how reconciliation matches seed entries to descriptor entries across reloads.

The scope is the namespace in which a key must be unique. Each container sets the scope for its children: 

  Page(key="survey")                  # scope for children: "survey"
  └─ Navigation(key="tabs")            # scope for children: "tabs"
     ├─ TextForm(key="name")               # full path: survey > tabs > name
     ├─ ChoiceForm(key="role")
     └─ BooleanForm(key="subscribe")

Two siblings may not share a key within the same scope (collisions silently overwrite state). Two components in different scopes can share a key with no conflict; the scope distinguishes them. That’s why you can have a name field inside every tab of a repeated structure — each tab is its own scope.

Keys also become URL path segments. A POST to the subscribe field goes to /pages/7e4b81cf/tabs/subscribe. The engine walks the path by key at request time to find the target component.

Rule of thumb. Keys are URL-safe lowercase identifiers (hyphens and underscores are fine, spaces are not). Pick keys that make sense in a URL path.

Sibling-reading components

Several component types read values from their siblings. This is where the engine’s reactivity lives.

  • Visibility — wraps a child and shows/hides it based on a sibling’s value
  • Switch — picks one of several named subtrees to render, keyed on a sibling’s value
  • ChoiceForm(options=SiblingBind(...)) — a Choice whose available options depend on a sibling’s value. Any component field can be made reactive the same way.
  • Computation — read-only display of a value computed from siblings (the graded() factory in engine/helpers.py wraps this for answer-key quiz grading)
  • Validation — cross-field rules (“end date must be after start date”)

Each takes a depends_on argument pointing at a sibling by key. Under the hood this is a SiblingRef, validated at bind time so typos and moves raise a clear error instead of silently breaking. 

# Example: show a follow-up only if role is "Other"
components=[
    ChoiceForm(
        key="role", label="Role",
        options=["Engineer", "Designer", "Other"],
    ),
    Visibility(
        key="other-detail",
        depends_on="role",              # sibling key
        predicate=lambda v: v == "Other", # show only when...
        component=TextForm(key="detail", label="Please specify"),
    ),
]

When role is anything but "Other", the wrapped TextForm does not render in HTML and does not appear in the JSON serialization. This is faithful projection, the subject of Lesson 5.

Dynamic repetition — Repeater

When the number of children is not known at seed time (“let the user add N line items”), Repeater stamps a template per dynamic entry. 

# A page with a button to add line items
Repeater(
    key="items",
    label="Line items",
    template=[
        TextForm(key="description", label="Description"),
        NumberForm(key="quantity", label="Qty", min_val=1),
    ],
)

Each added entry gets a unique compound scope (items/entry-abc123) so its children’s keys are isolated. The template is the shape; the Store holds as many copies as the user has created.

Groups — named compositions

When a particular composition is reused across pages, wrap it in a Group subclass. A Group has its own class identity in the registry, so instances can be spawned by type name at runtime. 

# A reusable Contact block
class Contact(Group):
    form = "contact"  # registry identifier

    def __init__(self, key, label):
        super().__init__(
            key=key, label=label,
            components=[
                TextForm(key="name", label="Name"),
                TextForm(key="email", label="Email"),
            ],
        )

Then anywhere: Contact(key="primary", label="Primary contact"). Same API as the built-ins.

Try it. In the Agent Portal, spawn a Component Gallery instance and click through the Containers tab — you’ll see all four Navigation modes, Group, Repeater, Visibility, and Switch demonstrated side by side with their seed code visible.

What you learned

  • Core Containers hold children via components=[...], steps=[...], template=[...], cases={...} — the parameter name depends on container type, the shape is the same.
  • Core Keys are unique within scope; each container defines its children’s scope. Paths through the tree become URLs.
  • Core Navigation does four behaviors with one class; pick the mode via prop.
  • Core Sibling-reading components (Visibility, Switch, Computation, Validation) express cross-field reactivity via depends_on; any other component can make a specific field reactive via SiblingBind.
  • Tip See the Agent Portal → Component Gallery for live examples of every container pattern.
