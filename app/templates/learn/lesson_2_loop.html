Four stages, one cycle

Every request to the engine walks the same four-stage loop. Understanding this loop is most of what you need to understand the engine. 

  1. DEFINE  →  2. BIND  →  3. SERVE  →  4. HANDLE  →  (back to 1)

After Handle, the next request starts again from Define. The server holds no long-lived in-memory component tree — every request rebuilds the tree from the seed plus the Store. That sounds expensive; it is not, because the trees are small and the JSON file reads are fast.

The reason for this design: the Store is the only source of truth for mutable state. There is no cache to invalidate, no session to reconcile. Every request sees the same authoritative state the last request wrote.

1. Define

The seed definition you wrote in Lesson 1 lives in pages/hello.py. At the top of every request, the engine re-imports the pages/ directory and looks for your definition variable. No restart needed when you edit a page; the next request picks it up.

A seed has structure but no identity. TextForm(key="name", label="Your name") describes “a field called name”, but it does not know whose name, or what value is currently stored. It is a template.

2. Bind

Binding attaches the seed to a Store — a per-instance JSON file at data/{instance_id}.json — and produces a live tree of bound components. Each child gets its scope (the namespace in which its key is unique) and URL prefix (where its HTTP routes live). 

# roughly what bind() does
page = Page(key="hello", components=[TextForm(key="name")])
bound = page.bind(data_dir=Path("data"), scope="a3f9c2d1")
# Now bound.components[0] has a Store reference and can read/write its value.

After bind, the tree is a working instance. Each component has a path like /pages/a3f9c2d1/name that uniquely addresses it. Each one can produce JSON or HTML on demand.

3. Serve

Two content types, same tree. For a browser: walk the tree, render each component to HTML via its Jinja template, stitch into a page. For an agent: walk the tree, call serialize() on each component, return the dict tree as JSON.

The serve step is pure — no mutation happens. It is a function of (descriptor, Store, Accept header) → response. 

# Pseudocode for the GET handler
def get_page(instance_id, accept):
    seed = discover_pages()[seed_key]
    bound = seed.bind(data_dir, scope=instance_id)
    if accept == "text/html":
        return bound.render()
    else:
        return bound.serialize()

4. Handle

A user clicks “Save”. The browser POSTs a JSON body describing the action: {"action": "set_value", "value": "Alex"}. The server receives the POST, binds a fresh tree, walks to the target component by URL path, and calls its handle(body) method.

The base handle() reads body["action"], looks it up in the component class’s _actions registry (a class attribute mapping action names to handler method names), and calls the mapped method with the body. TextForm maps set_value to a _set_value method that validates the input, writes to the Store, and returns the updated state. The response is the full re-serialized page, and the browser’s morphdom helper diffs it against the current DOM and mutates only what changed. 

# TextForm, roughly
class TextForm(Component):
    _actions = {"set_value": "_set_value"}

    def _set_value(self, body):
        value = body["value"]
        if self.min_length and len(value) < self.min_length:
            return self._error("Too short")
        self._store.put(self._scope, self.key, "value", value)
        return self.serialize()

The full trip

Concretely, a user typing “Alex” and clicking Save does this:

  1. Browser fires POST /pages/a3f9c2d1/name with body {"action": "set_value", "value": "Alex"}.
  2. Server reads the URL, calls discover_pages(), grabs the hello seed, binds to data/a3f9c2d1.json.
  3. Server walks the bound tree by path (name is a direct child), finds the TextForm.
  4. TextForm handle dispatches set_value to _set_value, which validates and writes "Alex" to the Store.
  5. Server re-serializes the whole page (cheap), returns HTML.
  6. Browser’s component.js receives the response, calls morphdom, which diffs the old DOM against the new and mutates only the changed nodes.
  7. User sees their new value. Focus, scroll position, any open <details> tags — all preserved because morphdom only touched what changed.
Notice what is NOT in that list. No session cookies. No server-side cache invalidation. No client-side state reconciliation. The Store JSON is the truth; the DOM is a projection of it; morphdom makes the projection feel live. This is the whole architecture.

Why statelessness matters

Because the engine builds a fresh tree every request, two things fall out for free:

  • Hot reloading. Edit pages/hello.py, save, refresh — no server restart. The next request re-reads the file.
  • Horizontal scaling. Any request can go to any server. There is no sticky-session requirement. The Store is just a file; swap it for a database later without changing the component logic.

The cost is the per-request overhead of reading a small JSON file and rebuilding a Python object tree. For the QMS workload (hundreds of components, not millions), this is fine.

What you learned

  • Core Every request walks four stages: Define (read seeds), Bind (attach Store + produce live tree), Serve (render or serialize), Handle (mutate on POST).
  • Core The server holds no long-lived component tree. The Store JSON file is the source of truth.
  • Core GETs are pure; POSTs mutate. Handling a POST produces a new full re-serialization; the browser morphs its DOM to match.
  • Tip “Restart needed?” — only for new component types. Editing a page definition, reloading in the browser is enough.

Next: the tree has three kinds of data — configuration, mutable state, and derived values. Each lives in a different place. Lesson 3 explains the categories and the rule that tells you which is which.
