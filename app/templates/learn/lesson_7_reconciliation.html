Three trees, one concept

There are three related but distinct trees in the engine’s head. Keeping them apart is the key to understanding everything in this lesson.

  • Seed tree — the Python definition in pages/*.py. Immutable at runtime. Holds callables (lambdas, validators, compute functions). Has no identity; it’s a template.
  • Descriptor tree — a JSON-serializable snapshot of a component tree. Lives on disk at __structure keys inside the Store. Can round-trip through JSON (no callables). Canonical source of truth for anything runtime-editable.
  • Bound tree — a live, scoped, Store-connected instance tree. What serialize() and render() actually run against. Rebuilt every request.
  pages/survey.py  →   seed tree
                            ↓ deepcopy + apply descriptor overrides
  data/survey-1.json  →   descriptor tree
                            ↓ reconcile (from_descriptor)
                       bound tree
                            ↓ bind(Store, scope, url_prefix)
                     bound tree (live)  →  serialize()/render()

The operation that produces the bound tree is called reconciliation. It’s the engine’s equivalent of what React does between two render trees.

__structure — the on-disk descriptor

Every container writes a __structure entry into its Store scope. That entry is the canonical record of what’s in the tree, in what order, with which props. 

# data/survey-1.json — concrete shape
{
  "survey": {
    "__structure": {
      "name": {
        "type": "text",
        "label": "Your name",
        "config": {"multiline": false, "min_length": 2}
      },
      "role": {
        "type": "choice",
        "label": "Role",
        "config": {"options": ["Engineer", "Designer", "PM"]}
      }
    },
    "name":  {"value": "Alex"},
    "role":  {"value": "Engineer"}
  }
}

Two sibling shapes live under the same scope:

  • __structure — the descriptor. Owns props (label, instruction, type-specific config).
  • Each child’s own key — owns state (the user’s values).

The __structure entry is written whenever structure is persisted. For a static page, it’s written once on first bind and re-read thereafter. For a mutable page (Lesson 8), __structure changes as the user adds, removes, or reorders components.

to_descriptor and from_descriptor

Two functions move between the tree and its descriptor. They live on the base Component class and in engine/registry.py: 

# Serialize a live component into its descriptor form
descriptor = component.to_descriptor()

# Rebuild a live component from a descriptor + optional seed
component = from_descriptor(descriptor, seed=seed)

Containers override to_descriptor to include their children’s descriptors. The result is always a plain dict tree, ready for JSON serialization.

from_descriptor is the tricky one. Its signature is: 

def from_descriptor(
    desc: dict,
    reg: ComponentRegistry | None = None,
    seed: Component | None = None,
) -> Component

The engine also exports reconcile = from_descriptor at the registry module level as a discoverability alias — readers arriving with a React mental model can find the operation under either name.

The algorithm

  1. Look up the descriptor’s type name in the registry ("text" → TextComponent).
  2. If a matching seed is provided (same type and key), deepcopy it. This preserves any callables the seed carries.
  3. Apply the descriptor’s scalar fields on top of the copy. The descriptor wins over seed defaults — the on-disk representation is authoritative.
  4. Recurse into children, matching seed children by key for the deepcopy step.

The deepcopy step is how callables survive the JSON round-trip they can’t actually make.

The callable-preservation problem

Some component fields hold Python functions: ComputedComponent.compute, DynamicChoiceComponent.options_fn, VisibilityComponent.predicate (when given a callable). Functions can’t serialize to JSON. The descriptor has no place for them.

This works fine in the normal case: the seed carries the callables, reconciliation deepcopys the seed, the callables end up on the bound instance. A re-bind on the next request re-matches the seed, re-copies the callables, and the page runs forever.

But consider what happens when the seed stops matching. Maybe you:

  • Rename a key in pages/survey.py — the descriptor still has the old key.
  • Delete a component from the seed — the descriptor still has an entry for it.
  • Add a new component via structural action — the seed has no entry for that key.

In any of these cases, from_descriptor falls off the seed-match path and enters “fresh construction” mode: it builds the component from the registry using just the descriptor’s config. No seed, no callables. The component renders and binds — but its callable fields are None. It does nothing. No warning is emitted.

This is a known silent failure mode. The mitigation today is that PageComponent threads the seed into every from_descriptor call during normal rebuild, so the gap only manifests when the seed and descriptor have genuinely diverged. The planned fix is to require the seed parameter for types declaring callable-valued fields, and return a typed diagnostic when seed-match fails — so the broken state is visible in the UI rather than silent.

SiblingRef — references that fail loudly

A parallel problem: components that depend on siblings (SwitchComponent, VisibilityComponent, DynamicChoiceComponent, ComputedComponent, ValidationComponent, ScoreComponent, ActionComponent) reference those siblings by key. If a referenced sibling gets renamed or removed, the reference goes stale.

Before the fix, a stale reference was a silent bug: the dependent component would look up a non-existent sibling, get back None, and produce no output. After the fix, references are SiblingRef values — a str subclass that additionally carries an optional expects type assertion. 

from engine.sibling_ref import SiblingRef

components=[
    ChoiceComponent(key="role", label="Role", options=["Engineer", "Other"]),
    VisibilityComponent(
        key="other-detail",
        depends_on=SiblingRef("role", expects=ChoiceComponent),
        predicate=lambda v: v == "Other",
        component=TextComponent(key="detail", label="Specify"),
    ),
]

The sibling-reading components coerce their depends_on field into a SiblingRef at construction time — so even plain strings get the treatment. Then, after bind, PageComponent._validate_sibling_refs() walks the whole tree, builds a map of all available sibling keys per scope, and checks every SiblingRef:

  • Does the referenced key exist in the correct scope? If not, raise SiblingRefError with the owner’s key, the missing target, the scope being searched, and the list of known siblings.
  • Does the referenced component’s type match expects? If not, raise with both the expected and actual type names.

The error is raised during bind — before serialize, before render, before any user action. You see it immediately when a page loads, not silently days later when a conditional branch fails to fire. 

# Example error message
SiblingRefError: VisibilityComponent(key="other-detail") references
sibling "role" (expects ChoiceComponent), but no sibling with that key
exists in scope "survey".
Known siblings: ["name", "role_choice", "subscribe"].

Field-type validation at the boundary

One more guard. When a prop changes at runtime (via _set_my_field for top-level fields or _set_my_config for config entries), the engine validates the value against the dataclass annotation. Literal["tabs","chain","sequence","accordion"] on NavigationComponent.mode means any attempt to _set_my_config("mode", "carousel") raises TypeError citing the allowed values.

Supported annotations: simple types (str, int, bool, float), optional forms (X | None and typing.Union), and Literal[...]. Permissive on complex types (Callable, list, dict) so unannotated fields never raise.

This is the type system the engine chose not to add via a library. It costs ~60 lines on the base class, runs only at mutation boundaries, and has prevented exactly the kind of silent corruption that descriptor-driven systems are vulnerable to.

What reconciliation does NOT do

Understanding what’s out of scope sharpens what’s in scope:

  • Does not walk into the bound runtime. Reconciliation produces an unbound tree. Bind is a separate step.
  • Does not validate descriptor shape. If a descriptor has an unknown key or mis-shaped children, reconciliation either fails loudly (unknown type) or silently accepts (wrong field types). The field-type validator runs at mutation boundaries, not at descriptor-load time.
  • Does not diff two descriptors. Unlike React’s reconciliation (which diffs old vs new render trees), this operation reconciles one descriptor against one seed. Descriptor diffing is not a concept here because the Store is the only source of truth.

Resilient bind

If the descriptor is corrupt — truncated JSON, missing fields, malformed structure — bind() and _rebuild() catch the failure and fall back to the seed. The page renders from the Python definition as if no descriptor existed. Mutable pages can be reset by clearing the __structure entry entirely.

This falls under the “don’t take the whole page down” principle established by the error boundary work in Lesson 6’s parity of concerns. One corrupt descriptor shouldn’t 500 a whole workflow.

Try it. Open data/{your-instance}.json in an editor. Change the label on one of the __structure entries. Reload the page in the browser — the new label appears immediately, no server restart. That’s reconciliation reading the descriptor you just modified. Now corrupt the JSON deliberately — delete a closing brace. Reload — the page falls back to the seed and still renders. The Store is the authority, but the seed is the safety net.

What you learned

  • Core Three trees: seed (Python), descriptor (JSON on disk), bound (live, Store-connected). Reconciliation builds the bound tree from the other two.
  • Core __structure is the canonical descriptor entry inside each container’s Store scope.
  • Core from_descriptor(desc, seed=seed) deepcopys the seed (to preserve callables) and applies the descriptor’s scalars on top.
  • Core Callable-preservation has a known silent failure mode when the seed stops matching. SiblingRef + bind-time validation closes the adjacent silent mode for sibling references.
  • Core Field-type validation runs at _set_my_field / _set_my_config. Supports Literal[...] for enum-like props.
  • Tip reconcile is an alias for from_descriptor. Either name works; both resolve to the same function.
