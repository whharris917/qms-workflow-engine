Two axes of mutation

The engine distinguishes two kinds of changes to a page:

  • Prop mutation — changing a field of a component (label, mode, min_length, multiline). The tree shape stays the same; a descriptor entry gets rewritten.
  • Structural mutation — changing the tree itself (adding, removing, moving, reparenting, grouping children). The descriptor grows, shrinks, or reshapes.

Both flow through the same mechanism: the descriptor changes, the next bind reads the new descriptor, the page renders differently. No in-memory tree is “edited” — the Store is the truth, and the next request produces a tree matching whatever the Store now says.

Edit mode — the ✏ pencil pattern

Every component has an editable flag. When it’s True, the wrapper renders a pencil toggle (✏) in the component’s chrome. Clicking the pencil enters edit mode; clicking ▶ returns to execution mode.

Edit mode changes the affordance surface. The label and instruction become inline editable inputs. Type-specific config (like multiline on TextForm, min_val/max_val on NumberForm) appears as a config panel. Containers gain add/remove/reorder controls. Nothing about the component’s state changes; only its props can be adjusted. 

# A TextForm that can be edited at runtime
TextForm(
    key="name",
    label="Your name",
    editable=True,         # show the pencil toggle
    multiline=False,
    min_length=2,
)

With editable=True, the user can rename the label, flip multiline, change min_length. All of these are prop changes; the underlying Python class is untouched. The edits persist to the parent’s __structure descriptor and survive reloads.

The two mutation APIs

Props split into two groups: top-level fields (label, instruction, editable) and type-specific config (multiline, min_val, mode, etc.). The engine exposes a helper for each. 

# Top-level field — writes to the descriptor's top-level scalars
self._set_my_field("label", "Full name")

# Type-specific config — writes to descriptor.config
self._set_my_config("multiline", True)
self._set_my_config("min_length", 3)

Both helpers do three things in sequence:

  1. Validate the type. The value must match the dataclass annotation (simple types, X | None, Literal[...]). Mismatches raise TypeError at the boundary — before any persisted state is corrupted.
  2. Update the parent’s descriptor. The parent container’s __structure entry for this child gets the new value written into its scalar fields or its config sub-dict.
  3. Update the runtime instance. setattr(self, name, value) so the current request’s tree reflects the change before serialize/render runs.

Step 3 matters because mutation often happens during _handle() of a POST, and the response serialization runs in the same request. Without setattr, the response would still show the old value; the user would wonder if their change took.

You never mutate self.label directly. Always go through _set_my_field / _set_my_config. Direct attribute assignment updates the instance but not the descriptor, so the change is lost on the next bind. It’s the runtime-only mistake that reconciliation quietly fixes by reverting.

Mutable pages — structure as state

Edit mode changes props. Mutable pages let the user change the tree shape itself — adding, removing, moving, reparenting components at runtime. Toggled at the page level: 

Page(
    key="builder",
    label="Page Builder",
    mutable_structure=True,   # enables structural editing
    components=[],               # can start empty
)

When mutable_structure=True, the page gains a toolbar and a structural editor. A type palette lets the user pick a component class; a canvas shows the current tree; drag-and-drop reorders children, reparents across containers, or groups selected items together.

Each interaction produces an action POST that the Page’s handle() dispatches via its _actions registry. The server-side actions are:

  • add_component — insert a new component by type name, at a position
  • remove_component — delete by key, surgically cleaning state from the Store
  • move_component — reorder within or between containers
  • reparent_component — drop into a new container
  • group_components — wrap selected siblings in a new Group
  • ungroup_component — splice a Group’s children into its parent
  • rebuild_from_seed — wipe __structure, start fresh from the Python definition

Each action mutates __structure. The next request rebinds, reconciliation reads the new structure, the tree renders accordingly. The seed definition doesn’t change; the instance deviates from the seed, and the deviation is persisted in the descriptor.

Surgical state cleanup

When a component is removed, any state it owned should be cleaned up — otherwise the Store grows forever with orphaned entries. remove_component walks the subtree being removed, collects every key at every scope, and calls Store.delete() on each. The Store provides a delete_scope() convenience for dropping an entire scope tree at once. 

# Pseudocode for what remove_component does
def _remove_component(self, key):
    target = self._find_in_tree(key)
    self._clear_subtree_state(target)        # Store.delete for each descendant
    self._pluck_from_structure(key)          # remove from __structure
    return self.serialize()                   # updated page state

Self-modifying pages — structural actions from Action

One more piece. Mutable pages give the user power to reshape the tree. Self-modifying pages let the page itself reshape in response to user interaction, under its own logic.

An Action’s action_fn callable can return a dict containing structural_actions in addition to its own state. Page intercepts those structural actions, applies them to __structure, and the page reshapes on the next serialize. 

# An Action that adds a follow-up question when triggered
Action(
    key="add-followup",
    label="Add follow-up question",
    action_fn=lambda context, store, scope: {
        "structural_actions": [
            {
                "action": "add_component",
                "type": "text",
                "key": f"followup-{counter}",
                "label": "Tell us more",
                "position": -1,
            },
        ],
    },
)

The engine supports this in the Survey Builder demo (pages/mutable_demo.py). A user answers a question; the Action fires; a new question materializes below it. The “fractal complexity plan” in the project history (Phase E) made this possible.

Use sparingly. Self-modifying pages are expressive but hard to reason about — the tree you see in the seed is not the tree at runtime. Reach for mutable pages when you need it (form builders, dashboards with variable content), reach for regular pages when you don’t. Static beats dynamic when static suffices.

Undo and snapshots

Edit mode maintains a per-component undo stack. Each mutation is snapshotted before it runs, and the ↩ chrome button pops the stack. A ✕ discard button restores the initial snapshot from when edit mode was entered — throwing away all edits and exiting edit mode.

Undo is local to the component in edit mode, not a global page-level operation. That’s a deliberate scoping choice: global undo would need to capture structural history across the whole tree, and the payoff didn’t justify the complexity. Per-component edit undo handles the common case cleanly.

What changes when

Putting it all together, here’s the mutation matrix: 

  USER ACTION              WHAT CHANGES                WHERE IT LIVES
  ───────────────────────  ──────────────────────────  ─────────────────
  Type into a text box     State (current value)       Store at key scope
  Click pencil             editable flag (prop)        parent __structure
  Edit label inline        label field (prop)          parent __structure
  Flip multiline toggle    config.multiline (prop)     parent __structure
  Drag new component in    Tree shape (structure)      parent __structure
  Drag component out       Tree shape (structure)      parent __structure + cleanup
  Click action button      Maybe structural_actions    varies
  Refresh browser          Nothing (GET is pure)       Store unchanged

All four columns of “where” resolve to one thing: some JSON file on disk. That’s why the engine’s resilience to crashes, restarts, and hot reloads is free — there’s nothing transient to lose.

Try it. In the Agent Portal, spawn a Page Builder instance. Drag a TextForm from the palette onto the canvas. Type a label. Drag a Navigation in. Group two children together. Each action’s POST body is visible as a tooltip on the button — you can see the structural-action protocol directly. Open data/{instance}.json and watch __structure change.

What you learned

  • Core Prop mutation changes the descriptor’s scalars; structural mutation changes the descriptor’s shape. Both flow through the Store; the next bind reads the result.
  • Core _set_my_field (top-level) and _set_my_config (type-specific) are the two mutation APIs. Both validate types at the boundary.
  • Core mutable_structure=True on a Page enables add/remove/move/reparent/group/ungroup via a structural editor and a public action protocol.
  • Core Action’s action_fn can return structural_actions, enabling self-modifying pages where user interaction reshapes the tree.
  • Core Edit mode keeps per-component undo via snapshot stacks. Discard restores the initial snapshot and exits edit mode.
  • Tip Everything on-disk. No transient in-memory state, no sticky sessions, no crash-recovery concerns. Reliability falls out of the design.
