What is a component made of?

Every component in Razem — whether it’s a simple text input or a complex navigation container — is built from the same small set of parts. Understanding these parts makes the entire system predictable: once you’ve seen one component, you know the shape of all of them.

Let’s walk through each part.

The parts

Label Identity

The component’s name, displayed as its heading. Every component has one. It’s what the user sees first, and it’s how the component identifies itself in affordance instructions and error messages. Set in the Python definition, overridable at runtime via edit mode.

TextForm(label="Full Name")

Key Identity

A unique identifier within the component’s scope (its sibling group). Keys are used for store paths, URL routing, and SiblingRef references. When omitted, a key is auto-generated as {form}-{8-char-hex}. You only need explicit keys when another component refers to this one.

TextForm(label="Full Name", key="name") # URL becomes: /pages/{page}/name # Store path: scope/name

Instruction Identity

Optional guidance text, displayed below the label in a lighter style. Instructions tell the user (or agent) how to interact with the component — what to enter, what format is expected, what the constraints are. If absent, no instruction line is rendered.

TextForm( label="Full Name", instruction="Enter your legal name as it appears on official documents.", )

Value State

The component’s current data — what the user has entered or selected. For a TextForm this is a string; for a ChoiceForm, the selected option; for a CheckboxForm, a list of checked items. The value lives in the Store (a JSON file on disk) and persists between requests. The shape of the value is type-specific.

Completion State

Every component exposes is_complete — a boolean answering “has this component collected enough data?” The rule is type-specific: a TextForm is complete when non-empty, a CheckboxForm when at least one item is checked, a container when all children are complete. The UI renders a green left accent and a completion ring when true.

Completion flows upward: a Page is complete when every child is complete. A gated Navigation (chain/sequence mode) uses child completion to control which steps are unlocked.

Affordances Protocol

The actions available on this component right now. Each affordance is a self-describing instruction: a label, an HTTP method, a URL, and a body template. Together they form a HATEOAS contract — the component tells you exactly what you can do with it, and exactly how to do it.

Affordances are state-dependent. A solved Rubik’s Cube stops offering rotation moves. A TextForm with data gains a Clear affordance. A component in edit mode offers different affordances than one in execution mode. The affordance list is the component’s instruction set at this moment.

# A typical affordance (serialized): { "label": "Set Value", "method": "POST", "url": "/pages/my-page/name", "body": { "action": "set", "value": "<value>" }, "instruction": "Set the text value." }

Dual rendering Protocol

Every component is rendered twice from the same serialized state: once as interactive HTML (for humans in a browser) and once as JSON (for AI agents via content negotiation). The HTML and JSON surfaces are faithful projections of the same underlying data — neither contains information the other lacks, enforced by parity tests.

The view toggle in the top-right corner lets you switch between them. Agents never see this toggle; they simply request Accept: application/json and get the JSON surface directly.

Edit mode Chrome

Components with editable=True gain a pencil button (✎) in their titlebar. Clicking it enters edit mode, where the label, instruction, and type-specific configuration become editable inline. In edit mode, the pencil is replaced by a play button (▶) to return to execution, an undo button (↶), and a discard button (✕).

Edit mode is a meta-level concern — it changes the component definition itself, not its value. It’s the difference between filling out a form and redesigning one.

How the parts compose

These parts are not arbitrary — they map to a program analogy. A component is a small program:

  • State (value + completion) = the program’s memory
  • Affordances = the instruction set — what operations are available
  • is_complete = the halt condition — when the program has collected enough input
  • The user or agent = the runtime that executes the program by choosing affordances

This analogy holds at every level of composition. A Page is a program whose instruction set is the union of its children’s instruction sets, and whose halt condition is the conjunction of its children’s halt conditions. Containers don’t add new concepts — they compose the same ones recursively.

Try it: Open any page in the Agent Portal and toggle between Human View and JSON. Match each part of the JSON output to the visual element on screen. Notice how affordances appear as buttons in HTML and as structured objects in JSON — same actions, two surfaces.

What you learned

  • Label, key, and instruction are the component’s identity — who it is, where it lives, what it expects.
  • Value and completion are its state — what data it holds and whether it has enough.
  • Affordances are its protocol — the actions it offers right now, state-dependent and self-describing.
  • Dual rendering projects the same state as HTML for humans and JSON for agents, kept in sync by parity tests.
  • A component is a program: state + instruction set + halt condition. Users and agents are the runtime.
