Where an affordance comes from

In Lesson 5 an affordance looked like a dict that magically appeared in responses. It isn’t magic. Every component generates its own affordances as part of serialize(), and the shape of the affordance is determined by a small class hierarchy in engine/affordances.py. 

# engine/affordances.py — the base dataclass
@dataclass
class Affordance:
    label: str
    method: str
    url: str
    body: dict = field(default_factory=dict)
    instruction: str | None = None

    def serialize(self) -> dict:
        result = {
            "label": self.label,
            "method": self.method,
            "url": self.url,
            "body": self.body,
            "render_hints": self._render_hints(),
        }
        if self.instruction:
            result["instruction"] = self.instruction
        return result

Subclasses override _render_hints() to tell templates how to render the affordance: a text input, a confirmation button, a simple button, a select dropdown. The hint is advisory — the rendering component is ultimately responsible for placing the affordance on the page.

A component generating its own affordances

Here is a simplified TextComponent serialization. Notice the affordances list: 

# TextComponent.serialize(), simplified
def serialize(self):
    value = self._store.get(self._scope, self.key, "value")
    return {
        "label": self.label,
        "value": value,
        "is_complete": self.is_complete,
        "affordances": [
            SetValueAffordance(
                label="Save",
                method="POST",
                url=f"{self._url_prefix}/{self.key}",
                body={"action": "set_value", "value": "<value>"},
                instruction="Submit the text value.",
            ).serialize(),
        ],
    }

Two things are happening here:

  1. The component reads its own state from the Store.
  2. The component builds an affordance list describing the actions it accepts. The URL is constructed from its own _url_prefix and key, so it always matches where the component lives in the tree.

Every component does this. The affordance URLs are never centrally declared; each component knows its own URL because it knows its own scope and key.

From data to HTML

Serialization produces a dict. Rendering produces HTML. The engine’s rule is that HTML is a pure function of the serialized dict — templates read the dict and emit markup. 

# Component.render() — always calls serialize first
def render(self) -> str:
    data = self._serialize_full()   # internal dict including render_hints
    return self.render_from_data(data)  # Jinja render from the dict

render_from_data picks the right Jinja template for the component’s type (with optional theme override), passes the serialized data as context, and returns the rendered HTML. Code paths never diverge: the dict is the source of truth.

Two-tier serialization

There are two serialization entry points:

  • _serialize_full() — the internal dict. Includes form, key, render_hints, and other fields templates need for HTML rendering. Used by render().
  • serialize() — the agent-facing dict. Strips internal fields that don’t belong in the API response. Used by the JSON endpoint.

This split matters because agents don’t need render_hints — they’ll never render HTML. Including those fields in the JSON would be noise. Stripping them at the serialize() boundary keeps the agent API clean without complicating the internal rendering code.

Templates render affordances via helpers

Jinja templates don’t hand-write button markup. Two helper functions in engine/templates.py do the work:

{% raw %}
# render_aff renders a full affordance as a labeled button or form
{{ render_aff(affordance) }}

# render_btn renders a minimal inline button with a specified CSS class
{{ render_btn(url, body, label, css_class) }}
{% endraw %}

Both helpers produce HTML with the data-c-* attributes that the global delegation script (component.js) listens for. When a user clicks the button, the script reads the attributes, builds a POST, sends it, and morphs the response HTML into the page.

The five URL-carrying attributes

Every clickable element that triggers a server action carries one of these attributes, each with its own handler: 

  data-c-post     simple POST with a pre-built JSON body
  data-c-submit   POST with a body built from the surrounding <form>'s inputs
  data-c-change   POST fired on input change (select, radio, checkbox)
  data-c-add      POST that adds a component (palette one-click)
  data-c-url      drag-and-drop target URL (reorder, reparent)

Parity tests walk the rendered HTML looking at exactly these attributes (and no others), so if you invent a sixth attribute you’ll need to teach the parity extractor about it.

Affordance flotation — the portal pattern

Some affordances are universal: every data component offers a Clear, every editable component offers an Edit mode, every container supports Batch. A naive serialization emits all of these on every component, producing lots of duplicated affordances at every level of the tree.

For agent consumers this is noise. An agent doesn’t need twenty copies of “Clear” — it needs one affordance saying “clear any of these twenty targets.”

The engine handles this with affordance flotation: deeply-nested affordances marked as “floatable” bubble up to the PageComponent level in the agent JSON, collapsed into one parameterized affordance per action kind. 

# An affordance opts into flotation by tagging itself.
# In _serialize_full():
aff = ClearAffordance(label="Clear", url=self._url, body={"action": "clear"})
aff["_floatable"] = "clear"   # merge marker

PageComponent walks the tree on serialization, collects every affordance carrying a _floatable marker, groups them by marker, strips them from children, and emits one compound affordance per group. Each compound affordance carries a structured targets dict mapping URLs to child labels: 

{
  "label": "Clear",
  "method": "POST",
  "body": {"action": "clear"},
  "instruction": "Clear the value of a specific component. POST the URL of the target component.",
  "targets": {
    "/pages/page-1/name":        "Your name",
    "/pages/page-1/description": "Description",
    "/pages/page-1/notes":       "Notes"
  }
}

The agent sees one action, the three target sites stay addressable by URL. HTML rendering is unaffected — the human UI still renders the three per-child Clear buttons where they live. Flotation is agent-tier only.

This is a Portal. In React, createPortal renders a child into a different DOM location than where the parent would imply. Here, the same idea applies to agent-facing JSON: the affordance originates deep in the tree but surfaces at the top. Same pattern, different medium. See /framing §2 for the full vocabulary mapping.

Parity tests — the invariant under CI

Faithful projection is an assertion: every action exposed to an agent has a clickable HTML counterpart, and vice versa. A page can only claim this property if it survives a mechanical check.

The parity test suite lives at tests/test_parity.py and currently runs 72 tests across 9 categories. It binds each page definition to an isolated tmp directory (no interaction with data/) and compares the two surfaces.

Per-page tests (10 pages × 7 tests each)

  • Shape — every page produces {affordances: [...], ...} with the expected keys.
  • No empty URLs — no non-chrome, non-disabled affordance is missing a URL.
  • Methods declared — every affordance with a URL also has a non-empty HTTP method.
  • Forward parity — every JSON affordance URL appears as an HTML action attribute (excluding chrome-rendered floated compounds, which are agent-JSON-only by design).
  • Reverse parity — every clickable HTML action URL is declared somewhere in JSON. Closes the opposite direction.
  • Action-name parity — where both sides declare an action name for the same URL, they match. Catches typos like set_valeu / set_value where the URL lines up but the body diverges.
  • URL resolvability — every JSON affordance URL routes to a real component via find_component. Catches URLs that parity-match but would 404 at runtime.

Pan-page tests (2 tests)

  • All pages render — every page produces non-empty HTML without exception.
  • All pages serialize — every page produces a dict with affordances.

How extraction works

The test suite has two extractors, one per surface:

  • extract_json_affordances(data) — recursive walk over the _serialize_full() output. Walks into parameterization dicts (targets, tabs, sections, steps, options) and synthesizes one affordance entry per target URL. This correctly treats O(N)→O(1) compound affordances as legitimately declaring all their per-target URLs.
  • extract_html_actions(html) — HTMLParser-based scanner for the five URL-carrying attributes listed above.

Running parity on a new page catches issues early: a typo in the POST body shape, a forgotten _floatable tag, a template that emits a button but doesn’t surface the URL in JSON. Shift-left.

Writing a new affordance

If you need a new kind of action — say, “Export this section as PDF” — here’s the shape:

  1. Subclass Affordance in engine/affordances.py. Override _render_hints() if templates need to distinguish it.
  2. In the component’s serialize(), emit an instance of the new affordance class. Give it a label, method, URL, and body shape. Add an instruction for agents.
  3. If the component needs to render it specially, reference render_hints.type in the Jinja template. Otherwise render_aff will produce a generic button.
  4. In the component’s _handle(), add a branch for the action name. Validate the body, mutate state, return the updated serialize().
  5. Run parity tests. If the new affordance floats, register its merge marker in PageComponent’s compound-affordance generator.

Five steps, each contained. The affordance system is designed to make new actions cheap to add without risking parity.

Try it. Open a page in the engine, view it as JSON (Accept: application/json), and grep the response for _floatable. You won’t find it — serialize() strips internal flags on the way out. Look at _serialize_full() directly (e.g., in a Python REPL) and you’ll see them. The distinction is small but matters for parity testing.

What you learned

  • Core Each component generates its own affordances in serialize(). URLs are built from the component’s own scope + key.
  • Core Two-tier serialization: _serialize_full() has internal fields for HTML rendering; serialize() strips them for the agent API.
  • Core Five data-c-* attributes carry all URLs in the DOM. The parity test knows about all five.
  • Core Affordance flotation is a Portal: floatable affordances bubble up to the PageComponent level in agent JSON, collapsed into parameterized compound affordances with targets dicts.
  • Core 72 parity tests (7 per page × 10 pages + 2 pan-page) catch URL/method/action-name mismatches at CI time.
  • Tip Read tests/test_parity.py end-to-end. It’s both the enforcement mechanism and the precise spec of what parity means.
